# Pango 1080p30 core package review (2026-10-29)

Scope: read-only review of `pango_1080p30_software_release(1).zip` (SHA256 `188bbfbb9a4f7e85b7e898a47f8d9a9a3f996f906038f332f266f93334132a44`). No RTL or bitstream was modified. The release bitstream SHA256 is `38ab1af1fc0fe1c15a7934d91b343679b0d4c999d788714bcf9b199b13a42ffd`.

## Findings, by priority

1. **P1: valid UART command can silently turn an entire corrected tile black.** `source/rtl/host_control.v:39-48,107-108` validates focal lengths, principal point, coefficient encoding, and gamma, but does not validate the affine registers or tile patch bounds. `source/rtl/tile_engine.v:87,263-265` treats a patch wider than 16 native words or taller than 256 rows as an empty tile. A reproducible input is the supplied calibration plus affine matrix `[[4,0,-1000],[0,1,0]]`, compiled by `host/model.py`. Its registers pass the RTL `parameters_ok` checks; output tile `(448,160)` has 2,048 valid mapped pixels and needs source x=784..1040, or **17** aligned 16-pixel words, so hardware marks the whole 64x32 tile empty and still publishes the frame. `host/model.py:90-105` rejects it, but the FPGA must not rely on this particular host program for safety. The `overflow_tiles` status increments, so the fault is diagnosable after publication, not prevented. Add an FPGA-side admission policy or ensure an overflow aborts publication; retain the host preflight as an additional check. This is an offline fixed-map reproduction, not a board test of the malicious command.

2. **P1 for the user's acceptance target: 30 distinct camera-to-HDMI frames per second is not established.** `tools/board_test.py:181-190` computes FPS from the core's published-frame counter. `source/rtl/tile_engine.v:226-231` increments that counter on publication, without a source-frame ID. `source/rtl/frame_bank_ctrl.v:20-27,72-89` can hand the newest already-completed source frame to the corrector again when no newer camera frame is available; `source/rtl/corr_slot_ctrl.v:42-43` can similarly keep the last display frame when the HDMI boundary arrives. The reported 45-degree sustained result, 5,414 publications / 180.4925 s = 29.9957 publications/s, is meaningful throughput evidence, but it cannot prove 5,414 distinct camera frames or 5,414 distinct HDMI frames. `tools/board_test.py:56-89` captures only three PNGs per scene and does not compute a sustained motion-frame uniqueness rate. The pass threshold is 29.5 publications/s, below the requested stable 30 distinct frames/s. Add monotonic camera-complete ID, corrected-source ID, and HDMI-latched ID/drop counters, then record lossless motion capture with timestamp/unique-frame analysis over a long window.

3. **P2: board image evidence cannot be independently replayed from this package.** `reports/board_runs/*/straightness_report.json` and `capture_test.json` reference `frame_21.png` through `frame_23.png` with SHA256 values, but the archive has zero board-run `frame_*.png` files. `tools/package_release.py:34-40` deliberately includes only JSON, JSONL, and TXT from board runs. The checkerboard RMS and nonblack image claims may be correct, but a recipient cannot recompute corner positions or verify the image hashes from this release. Include consent-cleared raw captures or an independently retrievable, hash-checked artifact.

4. **P2: thermal status remains unresolved.** `release/board_acceptance.json` records `configuration_status_over_temp_flag=true` and `junction_temperature_measured=false`; `BOARD_TEST.md` also records the flag. The cause could be status interpretation or actual device temperature. Do not classify this board as fully thermally accepted until PDS status semantics and a measured junction temperature are checked during sustained use.

5. **P3: release documentation contradicts its own acceptance record.** `README.md:5` and `release/README.txt:4` say the hardware was disconnected and no board test occurred, while `README.md:108`, `BOARD_TEST.md`, and `release/board_acceptance.json` report board tests. This appears to be stale pre-board wording, not evidence that the test logs are fabricated. Update the release text so the tested scope and remaining limits are unambiguous.

## Verified strengths and limits

- The release bitstream hash matches its manifest and board acceptance record. The seed3 PDS evidence ZIP contains the raw timing report and source hashes. All 139 listed source files exist and match those hashes. Its routed report states `All Constraints Met`; the 125 MHz DDR application setup WNS is **+0.593 ns** and hold WHS **+0.139 ns**, with zero failing endpoints. Reported resources are 9,786 LUT, 13,209 FF, 60 APM, and 84.5 DRM36K.
- The UART journals, JTAG SRAM programming receipt, and checkerboard straightness summaries are substantive board evidence. The claimed median checkerboard RMS improves from 2.674 px in bypass to 0.115 px corrected. The corresponding raw board PNGs are absent from the release, so this review did not independently recompute that metric.
- The nominal 45-degree board run reports zero core/write faults and zero patch overflows. The overflow issue above is an exposed-parameter boundary defect, not an observed failure in that nominal run.
- This package's row-major capture plus 64x32 output tiles and 256x256 patches is a credible alternative to the repository's direct 16x8 blocked-source proposal. Its board publication and positive routed WNS are stronger integration evidence for the tested command set. It does not yet settle the full camera-to-HDMI distinct-frame target, arbitrary accepted UART transforms, or thermal acceptance. Preserve both candidates while closing those gaps.
