# C69 transposed-source read trial (2026-10-28)

Status: isolated correction-read prototype. The production capture path still writes row-major source frames, so this RTL and the timing-only full-top build are **not** a usable board image. C50 seed7 remains the board-tested fallback. The purpose of C69 is to test whether a frame already stored in transposed order can support 90-degree correction at the 1080p30 publication target with a small on-chip cache.

The four files in `rtl/` derive from C63. `TRANSPOSE_SOURCE=1` swaps the mapped source axes before tag lookup and sampling, stores original source columns as transposed rows, reads each 1,088-pixel padded row with a 544-address-unit stride, and truncates the last 128-pixel segment to four 256-bit beats. The cache clamps the transposed horizontal coordinate at 1,079 and accepts source rows through 1,919. It uses the same coordinate mapper, 256-tag cache, bilinear interpolator, read bridge, and output writer as C63. `TRANSPOSE_SOURCE=0` retains the normal-source formulas, but that mode has not been fully regressed in this C69 directory.

The 125 MHz shared-DDR behavioral model in `evidence/system/` generated transposed source rows from an independent pixel function. A complete 1920x1080 90-degree frame passed the pixel, coordinate, lifecycle, DDR read and writeback checks. All 129,600 sampled golden pixels were within one RGB channel level. It published in 2,842,518 modeled cycles, or 43.975095 corrected frames/s, with 10,143 actual source segment reads and 75,084 source beats. The ideal trace model predicted 9,123 reads; cache pinning and pending requests account for the gap. Reproduce in an ASCII-only copy of this directory with `vsim -batch -do "do run.do"` from `evidence/system/`. The test model supplies a pre-transposed source frame; it does not measure the cost of producing that frame.

`evidence/timing/` contains the seed7 full-top PDS script, 125 MHz constraints, and raw report archive (SHA256 `4695D7787C2733336F5A04CD94CE5E23DD683344A77534FBD909F9294AD0BEDD`). The isolated full-top build at `D:/FPGA PDS/yx/C69_transposed_read_20261028/host` substitutes the C69 core and cache into the C63 design solely to assess mapped resource use and routed setup/hold timing. Routing completed. Independent `report_timing` shows slow-corner setup WNS **+0.056 ns**, minimum hold WHS **+0.055 ns** across corners, and zero failing endpoints. Device mapping uses 112/240 APM, 29.5/155 DRM, 20,778/66,600 LUT, and 25,691/133,200 FF. The worst setup path runs from `u_core/headq_rd[1]` through `sample_dispatch` to a core `state` clock enable. This margin is materially lower than C63's +0.445 ns and merits further optimization. The timing build's camera capture path remains row-major, so its output pixels would be wrong on hardware. Do not program its bitstream or promote it as an integrated solution. The 2022.2-SP6.1 DDR frame-buffer IP retains the existing FBG484-vs-FBG676 metadata warning.

Before a deployable arbitrary-angle candidate exists, implement a source producer that writes a transposed frame into a separate 4 MiB DDR slot, atomically publishes the completed slot, verifies the padded eight pixels per row, and measures capture/write/correction/display contention together. Use normal layout for small angles, transpose for steep angles, or validate a single blocked layout across angles. Rerun full-frame correctness, route setup/hold, and eventual board tests before replacing C50. The 43.975095 fps figure is modeled corrected-frame publication, not distinct camera-input or HDMI-display FPS.
