# R3 清理、复位和在途返回的适用范围

本补正只增补测试和观测断言，未改 cache、map、bilinear 或冻结读协议。既有读契约至多一个已受理逻辑事务，返回依序且最终 LAST；不能用清空测试模型来冒充旧事务已返回。

## 已实跑的独立缓存反例场景

`cache_boundary_r3_tb.v` 的 DDR 模型没有随 cache 的 rst_n/clear 清空 active。每次先实际 fetch&&grant 受理一笔，保持返回，清理或局部复位 cache 后，再把原事务的四拍全部送回。新代查找在旧返回前已经入队；依据单在途约束，在旧事务实际排空前不授予新加载。旧数据因 cache 无有效 load_active 被诊断为 load_error，不会置 tag_ready 或生成 load_done。随后用不同 seed 重载同一坐标，逐邻域核对可发现旧 RAM 内容误当新数据。

计数：清理后4拍、局部复位后4拍，8次预期拒绝；新代/并发采样6组通过；加载begin与采样同拍1次，返回与采样输入同拍2次，其中末拍1次，实际RAM写读重叠1次。并发发生在不同物理地址；被采样的 resident ID 未退休，不允许同地址覆盖。模型总受理14笔/返回56拍，旧事务没有被丢弃。

这里的 load_error 是特意施加协议外清理时的诊断，不意味着生产核心可以在任意在途位置清理后无错误续跑。

## 正常帧切换为何不能带着旧事务清理

核心中 i_frame_clear 的唯一来源为 `state==HOLD && i_corr_src_hold_gnt`。控制路径为：

```text
IDLE --合法frame_start--> HOLD --源槽受理/clear--> INIT_MAP
     --> RUN/READ_* --> DRAIN --> RELEASE --> DONE --> IDLE
```

忙时 frame_start 没有跳回 HOLD 的分支；定向 busy-start 注入只记录忽略事件，不强制 DUT 内部信号。

段路径：当前像素只有四个 ID 均 ready 后才能采样；ready 必须在其已受理加载完整 LAST 后建立。准备只覆盖实际2073600像素，不生成下一帧坐标；所有像素输出结束后，当前帧引用的加载已完成。整行路径：已受理预取期间控制处于 READ_WAIT，必须等 load_done 才回 RUN；每行预取限定 consume_y<1079，不在末行凭空加载下一帧。

六个全帧敏感性点和额外实际64拍点绑定的 `r3_r4_core_monitor.vh` 对每笔受理逐拍记账，检查：清理时已受理数为0、没有返回/请求或采样流水；释放时已受理/queued fetch/tag_pending/lookup/load均排空；LAST与剩余拍数相符。任何违反均 fatal；末尾还要求一次清理、一次busy-start忽略、全部受理拍精确返回。该检查不改变RTL，不以 queued-reset 替代 accepted-return。

因此正常帧清理沿既有 FSM 和数据就绪依赖排空，独立缓存中“旧受理返回跨清理”的故意反例不属于合法核心帧切换。全局 rst_n 在宿主来自 ddr_init_done；本回件不新增独立缓存复位控制口，也不承诺外部DDR未清事务时任意复位其中一级后立即续发仍能归属正确。

## 不扩展的边界

没有事务代号/epoch 的接口不能区分“新加载已受理后混入同形旧回复”。本测试遵守原单在途受理约束；未证明允许任意跨复位的新旧事务交叠。若管理方要求增加这种独立复位恢复能力，需明确桥/DDR的取消、隔离和重新受理规则后另行协商，不能单方面改冻结接口或把该场景宣称已支持。
